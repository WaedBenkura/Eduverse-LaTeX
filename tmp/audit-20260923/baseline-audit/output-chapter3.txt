Chapter 3. Methodology 17
3.1 Introduction
EduVerse combines interdependent workflows, roles, clients, services, and
configurable features that share data and access rules. Its methodology
therefore needed to support progressive refinement and controlled integration
as these dependencies became clearer during development. Methodology
choice was particularly important because access control, persistence, and
user interaction could not be refined independently without affecting the
coherence of the platform.
3.2 Methodological Approach
EduVerse was developed using a hybrid iterative methodology with
predominantly feature-based vertical-slice development, rather than a
strict waterfall model in which analysis, design, implementation, and
validation each occur once in a fixed sequence. The platform instead evolved
through repeated increments, each centered on a meaningful academic or
administrative capability, allowing requirements and structure to be refined
as the relationships between modules became clearer through development.
3.2.1 Iterative Feature-Centered Development
Development was organized around functional areas rather than technical
layers. Iterations focused on modules such as organization and class
management, materials, assessment, live sessions, results, AI Agent
and integrated IDE support, feature configuration, and public access.
Each selected feature moved through analysis, design, development, and
validation, with one increment informing the next. Organizing work in this
way kept each cycle tied to a recognizable user or institutional outcome
while allowing technical work to span the layers needed to deliver it.
The same iterations coordinated the primary web application with
the MVP mobile companion. They provided checkpoints for deciding
which high-frequency workflows required cross-client refinement and which
remained web-centered.

3.2.2 Vertical-Slice Realization
A feature was generally treated as a coherent functional unit rather than
split into interface-only or backend-only stages. Depending on scope, a slice
could span interface behavior, business rules, APIs, permissions, and data.
For example, assignment submission and examination scheduling depend on
the actor, governing rules, and persistence as well as the interface. The
approach was predominantly, not exclusively, vertical: some features required
only a subset of layers, while others also extended into the MVP mobile
companion. This qualification preserves an important distinction between
a methodological preference for complete feature paths and an inflexible
requirement that every increment modify every system layer.
3.2.3 Why This Methodology Fits EduVerse
A rigid sequential methodology was unsuitable because module boundaries
and dependencies became clearer through implementation. Organization
governance, class operation, assessment, communication, AI support, and the
integrated IDE share permissions, data, and user context; fixing their design
before examining that interplay would have increased the risk of rework.
Incremental checks allowed permissions, workflows, interfaces, and data
structures to be refined while remaining coherent with the wider platform.
Repeated validation was particularly important because the Organization
Administrator, Teacher, and Student interact with related features under
different access conditions, and some workflows span both web and mobile.
3.3 Repeated Development Cycle
Each increment followed the cycle in Table 3.1, with its depth adjusted to
the feature and the system layers involved. A web-centered change could
require limited supporting work, whereas another increment might extend
through the API, database, permissions, and mobile companion. In both
cases, the cycle retained the same progression from scope clarification to
platform integration.
Version control and pull-request review kept changes bounded to a feature
slice while supporting review of integration effects before merge.
