\section{Introduction}\label{sec:implementation_introduction}

Implementation is the applied outcome of the analytical and design phases in
which requirements, workflow models, database relationships, and interface
structures are transformed into an operable software system. In EduVerse, this
stage turns the platform from a set of governed academic models into a working
environment capable of supporting administration, class activity, assessment,
live collaboration, and assisted learning within one coordinated structure.

The implemented result is a web-first educational platform supported by a
mobile companion application. The web client carries the complete
administrative and academic workflows of the current system, while the mobile
companion extends selected high-frequency actions to mobile users without
claiming full parity. Across both clients, the implementation integrates the
web interface, the mobile companion, an authenticated shared API layer,
Supabase-backed relational data and authentication, AWS S3 file storage,
LiveKit-based live-session services, and OpenRouter-powered AI support. This
combination allows the platform to pursue security, operational coherence, and
future scalability without presenting incomplete capabilities as fully mature.

EduVerse was implemented as an integrated application stack rather than as a
detached frontend connected to a separately managed backend. The browser
client, the companion mobile client, the authenticated API layer, the database,

\section{System Architecture}\label{sec:implementation_system_architecture}

The implemented architecture follows a web-first, service-integrated model. The
web client renders role-sensitive pages and calls server-owned route handlers.
Those route handlers coordinate with Supabase for authentication, relational
data, and RPC-driven workflows, while AWS S3, LiveKit, and OpenRouter are used
for specialized capabilities that do not belong inside the relational database.

The same architectural logic extends to the mobile companion. The mobile
application does not implement a separate academic backend. Instead, it uses
Supabase for authentication and then calls the same EduVerse API layer with
bearer-token authorization. This shared-route model is important because it
keeps organization rules, role checks, and data-access behavior consistent
across clients.

At a high level, the implemented flow can be summarized as follows:

\begin{itemize}
  \item The client resolves the authenticated user and the active organization
    context before protected workspace data is loaded.
  \item Client actions call server-owned API routes rather than writing
    directly to academic business tables from the interface.
  \item The API layer validates input, enforces role and membership rules, and
    reads or writes structured academic data through Supabase tables and RPC
    functions.
  \item Large files, live-session participation, and AI generation are
    delegated from the server layer to AWS S3, LiveKit, and OpenRouter.
  \item Shared API behavior allows both the web application and the mobile
    companion to operate within one consistent access model.
\end{itemize}

This architecture directly supports one of the core goals of EduVerse: reducing
fragmentation without duplicating business logic across unrelated clients.

\section{Web Application Implementation}
\label{sec:web_application_implementation}

The web application is the main operational client of EduVerse. It implements
the broadest verified scope of the project, including organization management,
class participation, materials, chat, assignments, exams, results,
notifications, live sessions, whiteboard collaboration, AI support, and the
browser-based coding lab.

Its interface is structured around role-specific dashboards and class-centered
workspaces. Organization Administrators receive organization-scoped views for
membership, feature configuration, public access, teacher permissions, class
oversight, and settings. Teachers receive views centered on teaching activity,
grading, class management, and live-session control. Students receive views
focused on materials, submissions, results, notifications, live participation,
and enabled study tools.

At class level, the implementation treats the class as a unified academic
workspace rather than as a simple content folder. Chat, announcements,
materials, assignments, exams, results, live sessions, AI support, whiteboard
activity, and IDE access can all remain connected inside the same class when
those features are enabled. This is one of the main implementation-level ways
in which EduVerse addresses the fragmented-tool problem identified earlier in
the thesis.

The class model is also intentionally flexible. A class can support a standard
course, but it can also be configured for a narrower purpose, such as a digital
library class focused mainly on sharing books and learning materials. Public or
open-learning access can also be supported where organization policy enables
it, without removing the surrounding role and visibility controls.

\section{Mobile Companion Application Implementation}
\label{sec:mobile_companion_application_implementation}

EduVerse Mobile is implemented as an Expo and React Native companion
application written in TypeScript. It follows a provider-and-service
structure in which shared app state is centralized in a
top-level provider, while domain data is fetched through a dedicated API
service layer. Supabase is used for authentication and session persistence, and
the mobile client then calls the EduVerse backend through bearer-token-aware
requests.

In its current state, the mobile application already supports a meaningful set
of companion workflows:

\begin{itemize}
  \item authenticated sign-in, sign-up, password reset, and persisted mobile
    session handling;
  \item class summaries and dashboard-style overviews of current academic
    activity;
  \item notifications, unread-state handling, and update review;
  \item materials browsing, download, and local sharing;
  \item class chat for text messages and announcements;
  \item organization switching and profile-oriented utility actions;
  \item basic LiveKit-based live-session participation and manager-side start
    or end actions where permitted.
\end{itemize}

This scope is important, but it should not be overstated. The mobile client is
not a full replacement for the web platform. Administrative workflows,
organization management, feature configuration, rich assessment authoring, and
several advanced learning tools remain mainly web-side. The current mobile
scope also keeps assignment handling limited, with class
summary and progress information more developed than full mobile submission
workflows. Likewise, the mobile client provides basic live-session access, but
the richer whiteboard-centered experience remains primarily part of the web
implementation.

The academic significance of the mobile application therefore lies in extension
rather than parity. It makes high-frequency educational participation more
accessible while continuing to depend on the same governed platform model as
the web client.

\section{Backend, Database, and Storage Implementation}
\label{sec:backend_database_storage_implementation}

EduVerse uses a Supabase-centered backend model implemented from within the
Next.js project rather than through a separate standalone backend service.
Instead, server route handlers and shared libraries perform the main backend responsibilities: request validation,
authorization, workflow execution, persistence, and integration with external
services.

The data model is organized around several main domains: organization
membership and roles, class management, feature and extension settings,
materials and messages, assignments, exams, notifications, live-session
records, and historical academic data. Route handlers access these domains
directly where appropriate and also call Supabase RPC functions for operations
such as organization creation, role selection, class management checks,
results-visibility updates, public join workflows, and live-session claiming.

An important implementation decision concerns file handling. Large media and
document content is not stored directly inside the frequently queried
relational tables. Instead, EduVerse stores structured academic metadata in
Supabase while writing uploaded binary files to AWS S3. This separation keeps
routine database queries focused on structured records while still preserving
ownership, class linkage, and protected access to the associated files.

File handling is also server-mediated. Uploads are received and validated by
the server, written to S3 through protected credentials, and then registered in
the database. Download access is exposed through short-lived signed URLs, and
some material content can also be streamed through authenticated server routes.
This design keeps storage credentials out of client applications and aligns
file delivery with the rest of the platform's access-control model.

\section{Authentication, Authorization, and Security}
\label{sec:authentication_authorization_security}

Authentication in EduVerse is built on Supabase Auth. The implementation shows
sign-in, sign-up, password reset, authentication callbacks, and protected route
entry behavior. However, authentication alone is not enough for a
multi-organization educational platform. After sign-in, the system still needs
to resolve organization context, active role, and class-level permissions
before opening most protected workflows.

Authorization is therefore layered across several levels:

\begin{itemize}
  \item protected application-shell behavior for unauthenticated or
    incomplete-context access;
  \item route-level enforcement through authenticated server helpers;
  \item selected-role resolution for users who may hold more than one role;
  \item class-level membership and management checks through shared helpers and
    RPC functions;
  \item row-level security policies in the database migrations for major
    domains such as features, materials, assignments, exams, notifications, and
    live sessions.
\end{itemize}

The implementation also includes concrete security controls relevant to the
educational setting. These include server-side input validation, signed
time-limited file access, invite acceptance tied to authenticated email
identity, governed public join links, role-aware results visibility, exam
passcode protection, integrity-event recording, and audit logging. Webcam-based
proctoring and biometric monitoring are outside the current implementation
scope. Security is
instead built around authenticated access, scoped authorization, privacy-aware
data handling, and event-based assessment controls.

\section{Role-Based and Multi-Organization Access}
\label{sec:role_based_multi_organization_access}

One of the most important implementation problems solved by EduVerse is the
need for a single user to belong to more than one organization and, in some
cases, to operate under more than one role within the same organization. The
platform addresses this through organization-aware memberships, separate
membership-role records, selected-role state, and role-filtered API behavior.

In the codebase, the Organization Administrator role appears through internal
identifiers such as \texttt{org\_admin}. In the thesis terminology, however,
the more accurate and user-facing description is Organization Administrator.
This role is responsible for organization setup, invites, public access,
feature defaults, teacher permissions, class oversight, and related governance
workflows.

The same access model continues at class level. Teacher actions depend on the
organization rules and class assignment that apply to that user. Student access
depends on active role, class membership, feature settings, and visibility
rules. Organization-visible classes and public-access workflows widen access
only under explicit policy controls rather than as unrestricted exposure.

\section{Feature Availability and Extension Implementation}
\label{sec:feature_availability_extension_implementation}

EduVerse is implemented as a configurable platform rather than as a fixed set
of mandatory tools. The implementation includes feature definitions,
feature presets, organization-level feature settings, class-level feature
settings, organization extensions, and class extension settings. This allows
the same platform to adapt to different institutions, teachers, and class
purposes without splitting into separate products.

This design has practical academic value. A class that only needs materials and
chat should not be forced to expose exams, AI tools, or coding interfaces. A
class used as a digital library can stay focused on resource sharing. An
organization that does not want AI assistance can disable it. A teacher can
operate within the boundaries of the features that the organization or class
has enabled. In each case, the platform remains integrated while still allowing
controlled variation.

The same modularity improves future integration potential. Because core
behavior is expressed through protected shared APIs, the platform can support
companion clients or later reuse scenarios without moving academic business
rules into every consuming interface separately.

\section{Real-Time Communication and Live Sessions}
\label{sec:real_time_communication_live_sessions}

EduVerse implements both asynchronous and synchronous communication inside the
same class environment. Asynchronous interaction is handled through class chat,
announcements, and notifications. Synchronous interaction is handled through
live-session participation, session-state coordination, and the shared
whiteboard environment.

The live-session layer combines LiveKit and Supabase-backed session state. The
server issues room tokens, while session records are used to claim or end the
active session, maintain heartbeats, recover from stale-session conditions, and
notify connected clients about the current live state. This allows live
teaching to remain connected to class membership and class context rather than
becoming a detached external meeting.

Realtime participation also has a cross-client benefit. The web application
offers the richer live-session experience, including the integrated whiteboard,
while the mobile companion already supports basic live-session participation.
The two clients therefore contribute different depths of interaction without
breaking the shared session model.

\section{AI Learning Support and IDE Implementation}
\label{sec:ai_learning_support_ide_implementation}

AI support in EduVerse is implemented as an embedded academic service rather
than as a generic external chatbot. The implementation includes class AI Agent
routes, material extraction and summary generation, assignment-related support,
exam drafting assistance, and AI-backed feedback support through OpenRouter and
supporting helpers. These services operate with class context and role-aware
restrictions rather than as isolated text generation tools.

This is especially important for governance. AI is treated as one configurable
feature among others, which means it can be enabled or disabled at organization
level or class level. Student-facing assistance is also bounded by academic
rules intended to avoid direct final answers during active assessed work.

The same embedded-tool philosophy appears in the integrated coding lab. EduVerse
implements a browser-based IDE with a file tree, Monaco editor support,
templates, preview behavior, and browser-safe runners. The current system does
not expose unrestricted operating-system process execution. Instead, it keeps
the coding experience inside a safer browser-oriented model suitable for guided
educational use.

\section{Development Workflow and Deployment}
\label{sec:development_workflow_deployment}

The implementation was supported by a disciplined engineering workflow built
around GitHub branches or forks, pull requests, and pre-merge review. This
workflow complemented the iterative feature-based methodology described in
Chapter~3 by allowing changes to be developed as bounded slices, discussed, and
merged in a controlled way.

Automated quality checks also formed part of this workflow. GitHub Actions was
used to run project checks such as build, type, and format-related
verification before integration. Vercel preview deployments then provided a
reviewable running environment for inspecting role-sensitive pages, feature
gating behavior, and broader interface changes before merge.

This workflow matters academically because EduVerse is not a static report
prototype. It is a multi-role platform whose correctness depends on integration
quality. Branch review, automated checks, and preview deployments therefore
contributed directly to implementation reliability rather than serving as
incidental tooling.

\section{Implementation Challenges and Adopted Solutions}
\label{sec:implementation_challenges_adopted_solutions}

The implementation of EduVerse involved several recurring engineering
challenges. The most important ones, together with the adopted solutions, can
be summarized as follows:

\begin{itemize}
  \item Large educational media needed to remain accessible without weakening
    routine database performance. This was addressed by separating structured
    academic records in Supabase from binary file storage in AWS S3 while
    preserving metadata and access control in the main data model.
  \item Web and mobile clients needed consistent business behavior. This was
    addressed through a shared authenticated API layer so that both clients rely
    on the same server-owned workflow rules instead of duplicating them.
  \item The codebase needed to grow without collapsing into one monolithic
    feature set. This was addressed through a modular project structure with
    separate feature domains, shared libraries, and configuration-driven
    feature availability.
  \item Role-based access control needed to remain reliable across
    organizations, classes, and public-access scenarios. This was addressed
    through layered authorization, selected-role handling, membership-aware
    checks, and row-level security policies.
  \item New changes needed to be reviewable before they affected the shared
    platform. This was addressed through GitHub pull-request review, automated
    GitHub Actions checks, and Vercel preview deployments for safe visual and
    functional inspection.
\end{itemize}

These solutions show that the main technical contribution of EduVerse lies not
only in the presence of many features, but in the way those features were
organized so that storage, access control, client reuse, review workflow, and
academic governance remained compatible with one another.

\section{Chapter Summary}\label{sec:implementation_chapter_summary}

This chapter explained how EduVerse was implemented as a web-first,
multi-organization educational platform supported by shared protected APIs,
Supabase-backed data and authentication, S3-based file storage, LiveKit-based
live sessions, OpenRouter-based AI support, and a browser-based coding
workspace. It also clarified the role of EduVerse Mobile as a real but narrower
companion application under active development. The implementation also shows
how controlled feature enablement, governed public access, and future reuse
through shared APIs are built into the platform rather than added as
afterthoughts. The next chapter evaluates the implemented system through the
project's testing and validation scope.
