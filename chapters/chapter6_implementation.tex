\section{Introduction}\label{sec:implementation_introduction}

Chapter~5 described the structural design of EduVerse; this chapter explains
how that design was realized as an operational software system. It covers the
implementation of the web and mobile clients, shared server-side services,
persistence and file handling, authentication and authorization, configurable
features, real-time communication, AI support, the integrated coding
environment, and the engineering workflow used to integrate and review
changes.

The discussion focuses on implementation mechanisms and the distinct workflow
depth provided by the web and mobile clients.

\section{System Architecture}\label{sec:implementation_system_architecture}

The implemented architecture follows a web-first, service-integrated model. The
web client uses Next.js route handlers and shared server libraries to coordinate
authenticated application workflows. Supabase provides authentication and
relational persistence, while specialized services are used for capabilities
such as file storage, live communication, and AI-assisted operations.

After authentication, the mobile companion interacts with the same protected
EduVerse service layer used by the web application. This keeps access rules and
workflow behavior centralized across both clients.

Protected client actions are resolved through the server layer, where input
validation, organization and role context, permissions, and workflow conditions
are applied before persistence or external-service operations are performed.
This structure keeps academic business rules server-owned while allowing
different clients to expose different levels of interaction.

\section{Web Application Implementation}
\label{sec:web_application_implementation}

The web application is implemented with Next.js, React, and TypeScript and
serves as the primary operational client of EduVerse. Its structure combines
role-aware application routing with organization- and class-scoped workspaces
so that the active user context determines which interface and server
operations are available.

Web workflows interact with server-owned route handlers rather than embedding
academic business rules directly in presentation components. Shared server
utilities resolve authenticated context, validate requests, apply access checks,
and coordinate persistence or external-service operations.

The class workspace provides a common interaction shell for enabled academic
capabilities while preserving feature availability and role-specific behavior.
This allows the interface to remain consistent across classes even when the
available tools differ according to organization or class configuration.

The App Router separates authenticated workspace routes from public entry
routes. Shared context providers supply application state and compose the
authenticated shell with live-session and exam-lock state.

\section{Mobile Companion Application Implementation}
\label{sec:mobile_companion_application_implementation}

EduVerse Mobile is implemented with Expo, React Native, and TypeScript as a
companion to the primary web platform. Shared application state is coordinated
through the mobile provider layer, while domain operations are accessed through
a dedicated service layer that communicates with the protected EduVerse
backend.

Supabase provides mobile authentication and session persistence. Its mobile
client stores the session through AsyncStorage and refreshes authentication
tokens automatically. Authenticated service requests then attach the current
access token as a bearer token and reuse the platform's server-side academic
workflows rather than reproducing the web application's business logic inside
the mobile client.

The mobile implementation provides authentication, organization selection,
class summaries, notifications, material access, class communication, profile
utilities, and basic live-session participation. The web client provides the
broader administrative, configuration, assessment-authoring, and
whiteboard-centered live-session workflows, while the mobile client focuses on
high-frequency participation.

\section{Backend, Database, and Storage Implementation}
\label{sec:backend_database_storage_implementation}

EduVerse uses a Supabase-centered backend model implemented from within the
Next.js project rather than through a separate standalone backend application.
Next.js server route handlers and shared server libraries perform request
validation, authorization, workflow execution, persistence, and integration
with external services.

The relational backend follows the domain structures documented in Chapter~5.
Route handlers access the required tables directly where appropriate and use
Supabase RPC functions for centralized database operations. Examples
include \db{can_manage_class},
\db{set_selected_organization_role},
\db{is_class_feature_enabled}, and
\db{claim_class_live_session}.

Uploaded binary content is handled separately from relational academic
records. Server-side upload handlers validate incoming files, write permitted
content to AWS S3 using protected credentials, and persist the associated
academic metadata through the platform data layer. Protected downloads use
five-minute signed URLs, while material content can also be delivered through
an authenticated server route.

This server-mediated approach prevents storage credentials from being exposed
to clients and keeps file access subject to the authenticated academic context
of the surrounding workflow.

\section{Authentication, Authorization, and Security}
\label{sec:authentication_authorization_security}

Authentication is implemented through Supabase Auth, including account entry,
recovery, session handling, and protected-route access. Authentication
establishes user identity, but protected EduVerse workflows also require
organization, role, membership, and class context to be resolved before access
is granted.

Authorization is applied through multiple implementation layers, including
authenticated application entry, server-side route checks, active-role
resolution, organization and class membership checks, and database-level
protections where configured. Shared authorization helpers and permission RPCs
keep these checks consistent across protected workflows.

Row-Level Security policies defined in the database migrations provide an
additional access boundary for the schema areas to which those policies are
applied.

Additional security mechanisms include server-side input validation, protected
file access, controlled invitation and join workflows, role-sensitive result
visibility, exam passcode handling, integrity-event recording, and platform
audit logging.

\section{Role-Based and Multi-Organization Access}
\label{sec:role_based_multi_organization_access}

Multi-organization and multi-role access is implemented through organization
membership records, separate role associations, active-context selection, and
server-side access resolution. A single account can therefore participate in
more than one institutional context without requiring separate identities.

When a protected workflow is opened, the implementation resolves the active
organization and role together with the relevant membership or class
relationship. Server-side access checks then determine whether the requested
action is permitted in that context.

Internal role identifiers differ from some user-facing terminology used in the
dissertation. The Organization Administrator role uses the internal identifier
\texttt{org\_admin}, while the thesis consistently uses the user-facing term
Organization Administrator.

\section{Feature Availability and Extension Implementation}
\label{sec:feature_availability_extension_implementation}

Feature availability is implemented through shared definitions and
configuration records scoped to organization and class contexts. The resolver
combines definition defaults, organization settings, class settings, and parent
feature state. An organization-disabled capability cannot be enabled by a
class setting; a class can further disable a capability that remains available
to the organization.

The resolved configuration controls class navigation and guarded feature pages.
Protected AI and examination services also invoke the database-side
\texttt{is\_class\_feature\_enabled} check before executing their configurable
operations. Feature enforcement is therefore not limited to hiding interface
elements.

Extensions follow the same context-sensitive model. Organization extension
records define enabled extension entries, while class extension settings can
further restrict their exposure. Database validation prevents a class from
enabling an extension that is disabled for its organization.

\section{Real-Time Communication and Live Sessions}
\label{sec:real_time_communication_live_sessions}

Real-time learning in EduVerse combines LiveKit-based media participation with
platform-managed session state. An authenticated server route verifies class
membership or management permission before issuing a room-scoped LiveKit token,
while Supabase records coordinate the active class session and its lifecycle.

Session-state handling includes claiming or starting a session, marking it live,
ending it, and maintaining its \texttt{last\_seen\_at} activity timestamp. Host
clients send a heartbeat every 60 seconds, and server-side token and claim logic
uses a five-minute threshold when rejecting or replacing stale session state.
Supabase Realtime subscriptions propagate live-session record changes to the
application context.

The web application provides the richer synchronous interface, including the
integrated whiteboard experience, while the mobile companion supports a
narrower level of LiveKit participation through the same token and session
routes.

\section{AI Learning Support and IDE Implementation}
\label{sec:ai_learning_support_ide_implementation}

AI functionality is integrated through authenticated server-side routes and
supporting helpers that connect class context to OpenRouter-backed generation.
Supported workflows include contextual class assistance, material extraction and
summarization, teacher-facing assignment and examination drafting, and feedback
drafting for submitted work.

AI access is subject to class membership, management permission where required,
and the same class-feature check used by the wider configuration model. For
student-facing class assistance, the system prompt instructs the model to guide
learning without supplying direct final answers to active assessments. This is
a prompt-level academic guardrail, not deterministic answer filtering.

The integrated coding environment is a browser-oriented workspace with a file
tree, Monaco-based editing, project templates, virtual terminal commands,
lightweight language runners, and sandboxed HTML or Markdown preview behavior.
Supported operations execute through the browser-side runner model to provide a
browser-safe coding environment.

\section{Development Workflow and Deployment}
\label{sec:development_workflow_deployment}

Implementation changes were managed through version-controlled branches or
forks and pull-request review, supporting the feature-centered development
process described in Chapter~3. Merged pull-request commits provide traceable
integration of reviewed changes.

Three GitHub Actions workflows run on pushes and pull requests to the main
branch: a Next.js production build with Bun, a Biome formatting check, and a
TypeScript check using \texttt{tsc --noEmit}. The EduVerse web application is
deployed through Vercel, and each pull request generates a preview deployment
that provides a running environment for reviewing proposed changes before they
are merged.

\section{Implementation Challenges and Adopted Solutions}
\label{sec:implementation_challenges_adopted_solutions}

Four recurring engineering challenges shaped the implementation:

\begin{itemize}
  \item \textbf{Multi-organization and multi-role authorization.} Access
    decisions had to remain correct across memberships and roles. Selected
    context, shared authorization helpers, permission RPCs, and database
    policies work together to enforce access decisions.
  \item \textbf{Cross-client consistency.} Both clients needed consistent rules
    without duplicated business logic. They reuse protected server workflows
    while exposing different interface depths.
  \item \textbf{Large-file handling.} Binary files had to stay linked to
    protected records without entering relational queries. PostgreSQL holds
    metadata; server-controlled AWS S3 handles upload and retrieval.
  \item \textbf{Live-session state and recovery.} LiveKit participation also
    required a reliable class lifecycle. Persistent records, claim and end
    operations, heartbeats, and stale-state checks coordinate it.
\end{itemize}

This chapter described the technical realization of EduVerse across its web and
mobile clients, server-side services, persistence, security, configurable
capabilities, real-time communication, AI support, coding environment, and
engineering workflow. The implementation maintains a shared governed platform
model while allowing the web and mobile clients to provide different levels of
functional depth. The next chapter evaluates the system within the defined
