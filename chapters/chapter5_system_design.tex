\section{Introduction}\label{sec:system_design_introduction}

System design in EduVerse translates the analytical requirements of the
previous chapter into structures capable of sustaining governance, academic
workflows, and continued refinement. Because the platform combines
multi-organization administration, class-centered interaction, assessment,
live collaboration, AI support, configurable features, and extension points,
the design discussion must explain both the underlying information model and
the user-facing surfaces through which that model becomes operational.

The chapter therefore concentrates on the design elements that are most
directly supported by the verified implementation: the architectural context,
the database and storage model, and the implemented interface surfaces.
Together, these elements show how EduVerse connects persistence, governance,
and interaction instead of treating them as separate design concerns.

\section{Design Context and Architectural Structure}\label{sec:architectural_design_overview}

At design level, EduVerse is shaped by one central decision: related academic
functions should remain inside one governed platform even when they depend on
different technical services. The resulting structure combines a web-first
learning environment, a mobile companion scope, a Supabase-backed PostgreSQL
database, AWS S3-backed file references for uploaded academic content, and
LiveKit-related session metadata for synchronous learning. This architectural
context explains why the later database and interface decisions are organized
around shared roles, shared class context, and configuration-aware workflows.

\section{Information Model and Persistence Design}\label{sec:data_and_storage_design}

Persistence design in EduVerse is not only a matter of storage. The database
structure carries organization governance, role resolution, class membership,
visibility rules, feature enablement, and the academic workflows built on top
of them. This section therefore documents the verified database design of
EduVerse through the schema overview, the ERD, the physical schema tables
derived from the latest analysis notes, and the main uncertainty caused by
missing base-table DDL in part of the checked-in migration history.

\subsection{Logical Database Design}\label{subsec:database_design_overview}

EduVerse uses a Supabase-managed PostgreSQL database as the main persistent
store for organizational, academic, and operational records. The schema
follows a multi-organization structure in which the organization acts as the
top-level tenant, while the class operates as the main instructional
workspace. Within this arrangement, organization membership is modeled
separately from class membership so that role selection, invitation flows,
public join access, class rosters, and archived past-term history can evolve
without being collapsed into one table.

The current schema persists learning content through class materials,
chat-linked media records, assignments, assignment attachments, and
assignment submissions. Formal assessment is represented through exams, exam
questions, attempts, and answers, with released results stored directly on
assignment submission records and on exam attempt or answer records rather
than in separate results tables. Announcements are represented through
\db{class_messages}, AI persistence is limited to feature settings and
cached material summary or extracted-content fields, and the database does
not include dedicated tables for IDE workspace state or whiteboard state.
Viewed as a whole, the logical model is designed to support governance,
visibility, feature control, and academic continuity alongside conventional
data persistence.

\subsection{Relational Structure Through the ERD}\label{subsec:entity_relationship_diagram}

The ERD plays a central role in this design chapter because it expresses the
relational structure through which EduVerse operates before that structure is
expanded into the detailed physical schema tables. At this level, the diagram
does more than identify entities: it clarifies the cardinalities and junctions
that allow governance, academic activity, and configurable feature behavior to
coexist within one platform model.

At the core of the ERD, one organization can govern many classes, while one
user can belong to many organizations through membership records. Those
memberships do not collapse governance into one fixed permission entry; a
single membership can connect to one or more role records so that access can be
resolved according to the active context. The same many-to-many pattern appears
again at class level, where users participate in classes through class-membership
links rather than by direct ownership alone. Within each class, one-to-many
relationships extend to materials, messages, assignments, exams,
notifications, and live sessions. One assignment can receive many submissions,
and one exam can expand into many questions, attempts, and answers. Feature
settings then connect both organizations and classes to enabled or disabled
tools, allowing the same academic structure to behave differently according to
institutional policy.

These relationships matter because they are the basis of role-based access
control, organization governance, class visibility, assessment management, and
day-to-day academic workflows. They also explain why some relationships are
modeled through explicit junction tables rather than direct foreign keys alone:
users and classes, memberships and roles, and organizations and configurable
features all require many-to-many or context-sensitive resolution. The ERD
therefore provides the clearest design-level view of how EduVerse connects
institutional control with practical teaching and learning activity.

\subsection{Schema Interpretation Notes and Uncertain Relationships}
\label{subsec:database_design_notes_uncertain}

The original \db{CREATE TABLE} definitions for \db{organizations},
\db{profiles}, \db{organization_memberships}, \db{organization_invites},
\db{classes}, \db{class_memberships}, and \db{audit_logs} are not visible in
the checked-in migration history. Accordingly, the schema tables above record
only the columns and relationships confirmed by visible migrations, RPC
logic, and active query usage, while any non-visible link is labeled as a
logical relationship rather than an enforced foreign key.
